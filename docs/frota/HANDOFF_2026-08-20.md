# Handoff de 20/08/2026 — build sem internet, e o tema do Monitoramento

Continuação do [handoff de 19/08](HANDOFF_2026-08-19.md). Este não é só de Frotas:
o achado do build vale para **qualquer** publicação em homologação.

---

## 🔴 Um firewall com inspeção TLS travou homologação

Em 20/08/2026 um **Fortinet passou a inspecionar TLS** na rede de homologação.
Ele reapresenta todos os sites com certificado próprio:

```
issuer = O = Fortinet, CN = FGT80ETK19008643, emailAddress = support@fortinet.com
```

O servidor não conhece essa CA, então **toda saída HTTPS falha**: `github.com`,
`registry.npmjs.org`, `binaries.prisma.sh`, `registry-1.docker.io`. O relógio está
certo e o pacote de CAs está íntegro — o problema é o certificado interposto.

**Produção não é afetada** (AWS, fora dessa rede).

### O conserto de verdade

Instalar a CA raiz do Fortinet no servidor. Não é contornar o firewall — é passar
a confiar nele legitimamente. A inspeção continua, a empresa continua vendo o
tráfego; o servidor só deixa de recusar o certificado que o próprio firewall
apresenta.

```bash
sudo cp fortinet-ca.crt /usr/local/share/ca-certificates/
sudo update-ca-certificates
sudo systemctl restart docker      # o daemon tem seu próprio conjunto de CAs
```

O arquivo sai do Fortigate em *Sistema → Certificados → CA → exportar*.

### O que NÃO fazer

`git config http.sslVerify false` e `NODE_TLS_REJECT_UNAUTHORIZED=0` destravam em
um comando — e deixam o servidor aceitando **qualquer** certificado para sempre,
inclusive depois que a rede voltar ao normal. Não vale a pressa.

## Como publicar mesmo sem internet no servidor

A descoberta do dia: **quase nada do build precisa de rede.** Em vez de supor,
vale medir. O log mostra o que veio do cache:

```
npm install (frontend)   CACHED
npm install (api)        CACHED
passos 10 a 23           CACHED
npx prisma generate      ERRO  ← único ponto que sai para a internet
```

Havia 54 GB de cache de build no servidor, com 471 entradas. Como o
`npm install` fica numa camada **anterior** ao `COPY src`, mudança de código-fonte
não o invalida.

### 1. O código chega por SSH

O `deploy.sh` faz o servidor buscar o ref no GitHub, e é isso que falha. Mas o
modelo — "o servidor materializa um ref do git" — se preserva empurrando o commit
por SSH, que funciona:

```bash
git push planner@10.192.4.123:/home/planner/orkestri HEAD:refs/deploy/pendente --force
ssh planner@10.192.4.123 "cd /home/planner/orkestri && git checkout refs/deploy/pendente -- backend frontend"
```

### 2. Imagem base, se faltar

`node:20-alpine` havia sumido do disco (levada por alguma limpeza anterior). Sem
registro acessível, o build não tem de onde partir. Carregar de uma máquina com
rede resolve, e são só 47 MB:

```bash
docker pull --platform linux/amd64 node:20-alpine
docker save node:20-alpine -o node20.tar
scp node20.tar planner@10.192.4.123:/tmp/ && ssh planner@10.192.4.123 "docker load -i /tmp/node20.tar && rm /tmp/node20.tar"
```

### 3. O Prisma pedia um checksum de arquivo que já tinha

O `prisma generate` era a única linha do build que saía para a internet — e nem
era para baixar o engine. **O engine já está no `node_modules`**, posto pelo
postinstall do `npm install` (camada cacheada):

```
node_modules/@prisma/engines/libquery_engine-linux-musl-openssl-3.0.x.so.node
```

Ele baixava o `.sha256` só para conferir o binário que já tinha em disco.
`PRISMA_ENGINES_CHECKSUM_IGNORE_MISSING=1` (saída oficial do Prisma para rede
restrita) resolve esse passo — está no `backend/Dockerfile`, comentado.

**Ressalva:** com o checksum resolvido, o erro avança para o download do engine
em si (`libquery_engine.so.node.gz`). Então a variável **não** basta sozinha para
o build da API sem rede. O que funciona hoje é a via do item 4.

### 4. Construir só o que mudou

`docker compose up -d --build <serviço>` **arrasta as dependências** e tenta
reconstruir a API junto, mesmo quando só o frontend mudou. Separe:

```bash
docker compose -f docker-compose.yml -f docker-compose.override.yml build frontend
docker compose -f docker-compose.yml -f docker-compose.override.yml up -d --no-deps frontend
docker exec orkestri_nginx nginx -s reload
```

O build do frontend **não usa Prisma**, então passa sem rede.

### 5. Quando a API precisar mesmo ser reconstruída

Construa numa máquina com rede e carregue a imagem pronta:

```bash
docker build --platform linux/amd64 -t orkestri/api:latest backend/
docker save orkestri/api:latest | ssh planner@10.192.4.123 "docker load"
ssh planner@10.192.4.123 "cd /home/planner/orkestri && docker compose ... up -d --no-deps api"
```

**É seguro em relação à marca:** `MARCA` é lida em tempo de execução
(`process.env.MARCA` em `backend/src/common/marca.ts`), não gravada na imagem. O
compose de homologação define `MARCA: ${MARCA:-HUB Triunfo Transbrasiliana}`, e
isso sobrevive à recriação do container. Uma imagem construída em qualquer lugar
não leva "Orkiestri" para lá.

### 6. Verificação continua valendo

O `scripts/verificar-paridade.sh` compara o **git local** com os arquivos do
servidor — não precisa que o servidor alcance o GitHub. Continua sendo a resposta
para "o que está publicado".

## Monitoramento: a tela preta recuou para o Modo NOC

O módulo inteiro forçava escuro, sobrepondo o tema que a pessoa escolhe no topo.
O pedido foi: preto **só** no Modo NOC.

Não bastou tirar a classe `.mon-console`. As duas telas usam
`var(--mon-ok|down|warn|idle)` **39 vezes**, e essas variáveis moravam **dentro**
do escopo escuro — removê-lo apagaria as cores de disponibilidade junto.

Elas subiram para o `:root`, com **dois jogos de tons**: o verde que separa bem
sobre preto fica lavado sobre branco, e vice-versa. O jogo escuro é o mesmo de
antes, sob `[data-theme="dark"]`.

O que sobrou de `.mon-console` é o que nunca foi sobre cor: numeral tabular e raio
de canto.

**O Modo NOC não foi tocado** — nunca dependeu de `.mon-console`. Tem
`background: "#000"` próprio, em sobreposição de tela inteira.

Verificado no navegador, nos dois: o Monitoramento segue o tema (fundo claro com
tema claro) e o NOC segue preto.

## Um alerta sobre `docker builder prune`

A memória recomenda `docker builder prune -af` ao fim de sessões com muitos
builds, porque o disco enche. **Hoje isso teria sido desastroso**: foi justamente
o cache de 54 GB que permitiu publicar sem rede — sem ele, o `npm install`
precisaria da internet e não haveria saída nenhuma.

Enquanto a rede estiver interceptada, **não limpe o cache de build de
homologação**. Se o disco apertar, prefira remover imagens antigas
(`docker image prune`), nunca o cache de camadas.
